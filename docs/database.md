# Database

> Database architecture for the AI PC/Laptop Automation Agent.
> Source-of-truth: `database/base.py` (engine, session factory) and
> `database/models/schema.py` (all 22 ORM models required by master
> prompt §27).

## 1. Overview

The agent uses **SQLite** as its sole database, accessed through
**SQLAlchemy 2.x** with the new `Mapped` / `mapped_column` declarative
API. The choice of SQLite is deliberate:

- Zero-ops: no server to install or babysit.
- Single-file: trivially backed up by copying `db/custom.db`.
- ACID: needed because we audit every permission decision.
- Adequate for a single-user desktop app; tens of thousands of rows
  are well within SQLite's comfort zone.

The database lives at `/home/z/my-project/db/custom.db`. The path is
constructed in `database/base.py`:

```python
DB_PATH = Path("/home/z/my-project/db/custom.db")
DB_URL = f"sqlite:///{DB_PATH}"
DB_PATH.parent.mkdir(parents=True, exist_ok=True)

engine = create_engine(
    DB_URL,
    echo=False,
    connect_args={"check_same_thread": False},  # needed for FastAPI + SQLAlchemy
)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)
```

`check_same_thread=False` is required because FastAPI serves requests
on a thread pool while SQLAlchemy sessions are bound to the thread
that created them; we let SQLAlchemy work across threads but always
access a session through the `get_db()` dependency which yields a
fresh session per request.

Migrations are managed with **Alembic** (master prompt §27). The
repository layout will be:

```
database/
├── base.py
├── alembic.ini
├── migrations/
│   ├── env.py

│       └── ...
└── models/
    ├── __init__.py
```

The initial migration creates all 22 tables. Subsequent migrations
are append-only — never edit a published migration.

> `Base.metadata.create_all(bind=engine)`, which is idempotent and
> safe to call on every startup. Once Alembic is wired up, the
> startup path will instead run `alembic upgrade head` so older
> databases are migrated forward automatically.

Migration commands (planned):


## 4. Common conventions (§95)

Every table follows these conventions:

1. **Primary key** — UUID `String(36)` for entities (`User`,
   `Workflow`, `Task`, ...), autoincrement `Integer` for append-only
   logs (`TaskLog`, `AuditLog`, `ErrorLog`, `Setting`).
2. **Timestamps** — `created_at` on every table; `updated_at` on
   tables that get edited (`User`, `Setting`, `Permission`,
   `Workflow`, `AIProvider`, `AIModel`, `APICredential`,
   `DeviceProfile`, `Task`).
3. **UUIDs** — generated by `str(uuid.uuid4())` so they are
   portable across SQLite, Postgres (future), and JSON serialisation.
4. **Timezone** — all timestamps are UTC. `_utcnow()` returns
   `datetime.now(timezone.utc)`.
5. **Indexes** — per §95, on `workflow_id`, `task_id`, `status`,
   `created_at`, `scheduled_at`. See section 7.
6. **JSON columns** — used for flexible payloads
   (`plan_json`, `result_json`, `args_json`, `metadata_json`,
   `payload`, `request_json`, `response_json`). SQLite stores them
   as TEXT; SQLAlchemy serialises transparently.
7. **No plain-text secrets** — see section 8.

## 7. Index strategy (§95)

Per master prompt §95 the following columns are indexed. The schema
marks each with `index=True` on the column or via an explicit
`Index(...)` at the bottom of `schema.py`.

| Table | Indexed columns | Why |
|---|---|---|
| `workflows` | `created_at` | History listing sorted by recency |
| `workflow_versions` | `workflow_id` | Fetch all versions of a workflow |
| `workflow_nodes` | `workflow_version_id` | Fetch nodes for a version |
| `workflow_runs` | `workflow_version_id`, `status`, `started_at`, `created_at` | Dashboard "running now" query, history listing |
| `tasks` | `run_id`, `status`, `created_at` | Run detail page, history listing |
| `task_steps` | `task_id`, `status`, `created_at` | Step list, status-filtered views |
| `task_logs` | `task_id`, `timestamp` | Log timeline |
| `screenshots` | `task_id`, `created_at` | Screenshot carousel |
| `scheduled_jobs` | `workflow_id`, `next_run_at` | Scheduler tick query |
| `triggers` | `workflow_id` | List triggers for a workflow |
| `notifications` | `user_id`, `created_at` | Bell icon dropdown |
| `automation_history` | `task_id`, `status`, `created_at` | History page |
| `error_logs` | `timestamp`, `task_id` | Error dashboard |
| `audit_logs` | `timestamp`, `task_id` | Audit timeline |
| `permissions` | (none explicit; user_id implied FK) | Will add `idx_permissions_user_tool` in Phase 1 |
| `users` | `username` (UNIQUE) | Login lookup |
| `api_credentials` | (none explicit) | Will add `idx_creds_user_service` in Phase 1 |

Explicit composite indexes declared at the bottom of `schema.py`:

```python
Index("idx_tasks_status_created",   Task.status,    Task.created_at)
Index("idx_task_logs_task_ts",       TaskLog.task_id, TaskLog.timestamp)
Index("idx_audit_logs_ts",           AuditLog.timestamp)
Index("idx_workflow_runs_status",    WorkflowRun.status)
```

These cover the four hottest query patterns:

1. Dashboard "show me recent tasks by status" — `idx_tasks_status_created`.
2. Task detail "show me the log timeline" — `idx_task_logs_task_ts`.
3. Audit "show me everything since X" — `idx_audit_logs_ts`.
4. Dashboard "how many runs are running right now?" — `idx_workflow_runs_status`.

## 8. Secret storage

The database **never** stores plaintext secrets. This is enforced by
schema design, not by convention:

1. `api_credentials.credential_store_ref` is a string reference into
   the OS credential store. The schema column type is `String(255)`;
   there is no column whose name suggests a secret value.
2. `ai_providers` and `ai_models` carry only public configuration
   (model name, base URL, capabilities). No API key column.
3. `task_logs.payload` and `audit_logs.request_json` are scrubbed by
   the planned `SecretMasker` utility (see `docs/security.md` §8.3)
   before any write reaches the DB.

> The `SecretMasker` integration is **Phase 1 — Coming Soon**. Until
> it ships, the audit log payload deliberately omits the `args`
> field for tools whose name contains `credential`, `password`, or
> `token`. This is a coarse allowlist — the proper fix is the masker.

## 9. Backups

The SQLite database file (`db/custom.db`) is copied to
`db/backups/custom-YYYYMMDD-HHMMSS.db` on a daily schedule (Phase 2).
The backup uses SQLite's online backup API (`sqlite3.Connection.backup()`)
so the file is consistent even if writes are in flight.

Backups never include the OS credential store. The credential store
is backed up separately by the OS (Windows Credential Manager syncs
to the user's Microsoft account if they opt in; macOS Keychain syncs
to iCloud Keychain if enabled).

## 10. Querying the database

### 10.1 From the Python service

Use the FastAPI dependency:

```python
from database.base import get_db

@app.get("/tasks/{task_id}")
async def get_task(task_id: str, db: Session = Depends(get_db)):
    task = db.query(Task).filter(Task.id == task_id).first()
    if not task:
        raise HTTPException(404, "task not found")
    return task
```

In SQLAlchemy 2.x style:

```python
from sqlalchemy import select
from database.models.schema import Task

stmt = select(Task).where(Task.id == task_id)
task = db.execute(stmt).scalar_one_or_none()
```

```bash
WHERE wn.node_type = 'browser.click';
```

## 11. Initialisation

`database/base.init_db()` is idempotent:

```python
def init_db() -> None:
    from . import schema  # noqa: F401  — registers all models
    Base.metadata.create_all(bind=engine)
```

It is called:

1. At service startup — `lifespan` context manager calls
   `ensure_runtime_dirs()` which guarantees the directory exists
   before `init_db()` runs.
2. By the CLI: `python /home/z/my-project/scripts/init_db.py` (the
   original z-agent initializer — see worklog Task 1).
3. By the test suite — `conftest.py` (planned) creates a fresh
   in-memory SQLite database per test.

## 12. Schema versioning

The `_meta` table (created by `scripts/init_db.py` in the z-agent
scaffolding) tracks `schema_version`. The agent's schema doesn't
currently write to `_meta` — that integration is **Phase 1 — Coming
Soon**. When Alembic is wired up:

1. `alembic stamp head` writes the current revision id to
   `alembic_version` (Alembic's own table).
2. `alembic upgrade head` runs all migrations forward.
3. The service's startup `lifespan` runs `alembic upgrade head`
   before accepting HTTP traffic.

Until then, `init_db()` creates the full schema in one shot. Existing
databases that were created before a schema change must be deleted
and recreated during the MVP. Once Alembic is in place, this caveat
goes away.
